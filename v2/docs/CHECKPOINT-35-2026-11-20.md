## Changes
1. Added migration 006_vio_storage_cleanup_reference_guard.sql.
2. Queue insert/path changes and metadata reference creation/update acquire the same transaction-scoped advisory lock derived from bucket and storage path.
3. A pending cleanup queue row reserves the object. New references to that object are rejected until the job is finalized.
4. Guard triggers cover expression assets, character accessories, and profile background references.
5. Trigger functions use SECURITY DEFINER with a fixed search_path because the cleanup queue is intentionally unavailable to authenticated clients under RLS.
6. Added a regression test for the reservation lock, pending-job check, all three metadata guard triggers, and profile JSON reference extraction.
7. Updated v2 README migration instructions through migration 006.

## Safety and scope
- The guard is additive and is not applied to any Supabase project by this commit.
- No Edge Function deployment, Supabase migration execution, or production Pages change was performed.
- Existing v1.0, Offline v1.7, Online v1.0, production main, and backup branch remain untouched.
- A failed or pending cleanup job intentionally blocks re-referencing that exact object. This favors preventing dangling references over silently reusing an object scheduled for deletion.
- Existing references are not blocked by unrelated profile/asset edits when the referenced bucket/path remains unchanged.
