# Vio Studio v2.0 — Checkpoint 45
Date: 2026-11-21

## User-reported regression
After Checkpoint 44, the user confirmed that the clean OBS overlay can render the avatar PNG, but reported:
- Solo OBS overlay did not visibly use the complete saved character/profile configuration.
- No microphone input control appeared inside the clean OBS link.
- GO Collaboration showed participant avatars, but personal room settings and avatar layout did not reliably load/apply.

Screenshots showed:
- GO Collaboration room code 8307.
- Avatar layout controls with scale 0.80x, horizontal position 19, vertical position -1.
- Microphone input selector and Mic ON state in the Creator app.
- Avatar rendered in the shared stage.

## Source and database investigation
1. `overlay.js` does not own microphone capture or an input selector. It is a clean rendering endpoint. Mic state is intended to come from the signed-in Creator app over the room's private Realtime channel. This keeps settings controls out of the OBS output.
2. The login sequence started `AudioEngine` before `loadCurrentProfile()`. A later `setOptions({deviceId})` only changes the engine's options; it does not replace the already-open MediaStream. A saved microphone device could therefore be ignored after login.
3. `loadRoomMembers()` only rebuilt `roomOverrides` when the backend returned a truthy room override object. If a room had no saved override, stale values from a previously visited room could remain in the controls, even though the renderer used profile defaults.
4. The Solo OBS link creation path subscribed to the room and loaded members but did not explicitly publish the Creator's current mic state after subscription. A state transition would eventually publish, but the initial state could remain stale until the next transition.
5. Development DB inspection confirmed the profile has an active character and four expression assets. The inspected profile includes saved scale, mirror and effects settings. The currently active personal overlay room was room 5680. The screenshot's room 8307 was present in the Development DB but was closed by the time the audit query ran. Do not treat the screenshot room as the currently active room.

## Changes in this checkpoint
- Reordered login initialization: load saved profile/audio preferences before opening microphone capture.
- Rebuilt room override state on every room-member load using profile defaults plus that room's own persisted overrides. This prevents old room-local slider values leaking into a new room.
- When the effective room microphone device differs from the currently opened device, stop and reopen the stream if the mic was active; update sensitivity and boost in place.
- Solo OBS link generation now requests microphone permission from the Generate button gesture if capture is off. If permission is not granted, the visual link is still generated with an explicit warning.
- After a new Solo room subscribes and loads its members, publish the current microphone state immediately.
- Added regression tests for login ordering, room override reset/device switching, Solo mic-state publication, and profile/active-character data being passed to the shared renderer.

## Microphone architecture clarification
The generated OBS link remains a clean, menu-free renderer and does not expose a microphone selector. The Creator app owns microphone selection/capture and broadcasts the talking/idle state to the overlay. The microphone audio itself is not routed as a voice-monitoring signal through the avatar renderer; this system is for voice-activity detection and expression switching. If actual microphone audio is needed in the OBS mix, add the physical microphone as a separate OBS audio input source.
